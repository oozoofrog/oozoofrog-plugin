# Outcome Brief

사용자가 더 나은 지시 방법을 배우거나 작업 지시서를 개선하려 할 때 적용한다. 현재 지시가 낡았다고 가정하지 않는다. 결과물과 실제 실패를 기준으로 필요한 부분만 바꾼다.

사용자의 기존 팀 운영·모델 선택·도구·권한과 작업 우선순위를 유지한다. 현재 요청의 팀·검수 규칙이 있으면 따르고 작은 일에 팀을 계속 늘리지 않는다. 전역 규칙과 충돌하는 변경은 제안만 한다.

1. 이미 주어진 맥락에서 결과물, 입력, 보존할 제약, 관찰 가능한 완료 기준을 뽑는다. 사소한 선택은 모델에 맡기고, 결과를 크게 바꾸는 미정 결정만 사용자에게 묻는다. 추가 질문 없이 가능한 초안은 먼저 만든다.
2. 작업에 필요한 출처·도구·검증을 고른다. 모든 작업에 논문, 페르소나, 긴 계획, 반복 검수를 붙이지 않는다. 최신 제품·모델 주장은 로컬 공식 자료를 먼저 확인하고 부족하면 공식 출처로 검증한다. 모델/제품/환경·확인일을 기록한다. 비공개 내부 생각을 요구하는 대신 결론, 핵심 근거, 가정, 확인 결과를 요청한다.
3. 사용자가 정한 시간/비용/도구 제한을 지킨다. 미정이면 작은 첫 단계와 종료 조건을 제안한다. 실제로 측정하지 못하는 토큰·금액·팀 전체 시간을 추정치로 채우지 않는다. 권한 거절과 실행 여부 불확실은 별도 기록하고 임의 재시도하지 않는다.
4. 코칭에는 사용자의 사례 하나를 사용한다. 짧은 예제 → 한 번 시도 → 구체적인 피드백 순서로 진행한다. 지금 긴 설문을 보내지 않는다. 예시를 보고 배우는 것과 스스로 작성해 확인받는 것을 구분한다.
5. 비교가 유용하면 [방법과 A/B 기록법](references/method.md)을 읽는다. 동일 입력·모델·환경·평가기준에서 지시 방식 한 요소만 바꿔 작은 A/B를 설계한다. 한 쌍의 결과는 그 과제 관측이며 일반 성능 증명이 아니다. 실제 실행과 설계만 된 실험을 분리한다.

작업별 지시가 필요하면 [최소 템플릿](references/templates.md)을 읽는다. 빈칸을 전부 채우게 강요하지 말고 현재 작업에 필요한 항목만 쓴다. 최종 전달에는 결과물, 수행한 검사, 미검증 범위와 다음 판단을 짧게 적는다. 설치된 파일, 새 세션에 노출됨, 실제 적용됨은 각각 다른 상태다.

방법의 근거·모델별 차이를 설명할 때는 [확인한 출처와 한계](references/sources.md)를 읽고, 이후 제품 변경 가능성이 있으면 다시 확인한다. 확인된 권고를 사용자에게서 실측한 효과라고 말하지 않는다.
