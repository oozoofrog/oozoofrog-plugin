# 리팩토링

기존 동작을 보존하면서 변경 이유와 의존 관계를 명확하게 만든다. 기계적 진단으로 조사 위치를 좁히고, 실제 코드 구조를 근거로 사용자에게 원하는 범위를 직접 묻는다. 범위가 확정되면 분석에서 멈추지 않고 구현·검증까지 진행한다. 분석 전용 요청은 읽기 전용으로 수행한다.

## 1. 먼저 조사하고 범위를 질문한다

- 사용자 요청에서 시작점을 찾는다. 대상이 없으면 저장소의 최상위 구성과 진단 분포로 후보를 찾는다. 사용자에게 파일 목록부터 요구하지 않는다.
- 가까운 저장소 지침, lint/formatter 설정·버전·CI 실행기, 타입 검사·테스트·빌드 명령을 확인한다. 작업 트리와 대상의 기존 diff를 확인하고 사용자 변경을 보존한다. reset, 자동 stash, 일괄 포맷으로 작업을 덮지 않는다.
- 파일명·심볼·의존 관계부터 확인한다. 기존 진단이 현재 입력과 일치하면 재사용한다. 그렇지 않으면 설정된 도구의 수정 없는 진단을 먼저 실행한다. Swift가 대상에 포함되면 [Swift 지침](references/swift.md)을 읽고 SwiftLint 진단을 필수로 사용한다. 분석 전용 요청에도 적용한다. 현재 입력·설정·도구 버전이 같은 유효한 진단은 재사용할 수 있다. 진단을 확보하지 못하면 Swift 검토·리팩토링을 완료로 보고하지 않는다. 다른 언어는 저장소의 기존 도구를 따른다.
- 진단을 파일·규칙·위치별로 묶고 상세 읽기 대상을 고른다. 도구 실행 실패와 출력 파싱 실패를 "위반 0개"로 취급하지 않는다. 유효한 텍스트 출력이 있으면 사용하고 진단을 확보하지 못한 범위를 기록한다. 전체 파일이나 로그를 먼저 읽지 않는다. 선언·호출 관계와 필요한 코드 구간을 읽어 기능 본체, 소비자, 공용 의존성을 구분한다. lint가 잡지 못하는 업무 규칙 중복·책임 혼합·숨은 부수 효과도 필요한 범위에서 조사한다.
- 실제로 존재하는 경계로 2~3개 범위 후보를 제시한다. 각 후보에 포함 대상, 필요한 호출부 조정, 제외 대상, 영향과 추천 근거를 짧게 적는다. 후보가 하나뿐이면 그 범위를 구체적으로 제시해 확인한다.
- **사용자에게 직접 원하는 범위를 질문하고 답변을 기다린다.** 선택형 질문 도구가 있으면 사용하고 자유 입력도 허용한다. 없으면 대화에서 묻는다. 범위 답변 전에는 소스·테스트·설정 수정과 lint 자동 수정을 시작하지 않는다. 진단 로그·캐시와 이미 허용된 도구 준비는 소스 수정과 구분한다.
- 사용자가 이미 구체적인 경계를 명시했거나 "리팩토링할 범위는 네가 결정해"처럼 범위 결정을 명시적으로 위임했다면 재질문하지 않는다. 적용할 경계를 짧게 명시한다. 단순한 "관련 모듈", "알아서 리팩토링", "구현까지 완료"는 공용 모듈까지의 범위 위임으로 간주하지 않는다.

시간 압박, 진단이 가리키는 파일, 다른 작업자의 제안만으로 범위를 대신 확정하지 않는다. 범위가 확정된 뒤에는 매 단계 승인 질문을 반복하지 않는다. 사용자가 확정하거나 위임한 범위를 벗어나는 실질적 확대만 이유와 영향으로 다시 질문한다. 명시적 위임 안에서 경계를 조정할 때는 근거를 알리고 진행한다.

## 2. 기준선과 변경 근거를 정한다

- 확정 범위의 호출부·의존 모듈·관련 테스트를 필요한 구간까지 읽는다. 진단이 없다는 이유로 책임 검토를 생략하지 않는다.
- 변경 전 관련 검사 결과를 기록한다. 명령, 도구 버전, 설정, 대상, 종료 상태, 진단·테스트 수, 실패 내용과 로그 위치를 남긴다. 기존 실패, 신규 실패, 실행 불가를 구분한다. 기존 근거의 입력이 같으면 재실행하지 않는다.
- 각 변경 후보를 `위치 → 실제 변경 이유 → 영향 범위 → 개선 방향 → 검증 방법`으로 요약한다. SRP의 기준은 하나의 변경 이유다. 함께 변경되는 응집력 높은 코드는 유지한다.
- 업무 규칙·계산과 UI·I/O·상태 변경은 분리 효과가 있을 때 나눈다. 핵심 처리 순서를 보여주는 조율 함수는 명확하게 유지한다.
- 함수·파일의 줄 수만으로 분할하지 않는다. 프로젝트 구조와 명명 관례를 우선한다. 범용 utils, 근거 없는 공통화, 불필요한 인터페이스·클래스·계층, 순환 의존성과 공개 API 확대를 피한다. 모양이 비슷해도 업무 개념이 다르면 합치지 않는다.
- 짧은 변경 계획을 설명한 뒤 확정 범위는 구현한다. 실제 개선 근거가 없으면 변경을 만들어내지 말고 검토 결과를 보고한다.

## 3. 동작을 보존하며 작게 변경한다

- 기계적 lint/formatter 수정과 구조 리팩토링을 별도 단계로 진행한다. 자동 수정 결과도 diff로 확인한다. 대상 밖 수정은 이번 변경에 필요한 호출부·의존 관계 조정으로 제한한다.
- 복잡한 로직에 검증이 부족하면 정상·실패·경계 조건의 외부 동작을 기록하는 특성화 테스트부터 추가하고 기존 코드에서 통과를 확인한다. 구현 세부사항을 그대로 복제하는 테스트는 피한다. 저장소가 요구하는 별도 회귀 검증 절차도 보존한다.
- 공개 API, 반환값, 오류 처리, 부수 효과와 실행 순서를 유지한다. 비동기 처리에는 취소·격리·동시성 의미, 저장 작업에는 트랜잭션 경계, 재시도에는 조건·횟수·순서, 캐시에는 갱신·무효화 의미를 확인한다.
- 책임 단위로 수정하고 관련 검사를 실행한다. 분리 후 전달 인자·간접 호출·결합도가 더 늘었는지 검토한다. 발견한 버그와 기능 개선은 별도 후속 항목으로 기록하고 섞지 않는다.
- lint 통과를 위해 규칙·기준선을 완화하거나 disable 주석, 타입 검사 우회, 테스트 삭제·약화를 사용하지 않는다. 합리적인 분리로 해결하지 못한 경고는 미해결로 보고한다.
- 동작 근거가 없고 그 근거가 변경 판단에 필수이면 해당 변경을 멈추고 질문한다. 독립적으로 진행 가능한 확정 작업은 계속한다. 의존성 설치, 외부 작업, 배포 등에 대한 실제 사용자·저장소 권한을 따른다.

## 4. 검증하고 결과를 보고한다

- 단계별 관련 검사 후 저장소에서 요구하는 lint, 타입 검사, 테스트와 빌드를 수행한다. 관련 입력이나 실패·우려가 바뀌지 않은 읽기와 검사를 반복하지 않는다. 필요한 전체 회귀 검사는 생략하지 않는다.
- 최종 diff에서 의도하지 않은 동작 변경, 사용자 변경 손상, 불필요한 파일, 과도한 추상화, 분리 후 증가한 결합도를 확인한다. Git 저장소에서는 diff 공백 검사도 수행한다.
- 실패 비교는 총 개수만이 아니라 규칙·위치·메시지 또는 테스트 식별자를 사용한다. 파일 이동·줄 이동으로 인한 진단 이동과 실제 신규 실패를 구분한다. 입력·환경이 달라 비교가 불확실하면 그 한계를 적는다.
- 전체 로그는 저장소의 정해진 근거 경로에 보관한다. 정해진 경로가 없으면 저장소 밖 작업 디렉터리를 사용한다. 분석에는 구조화한 요약과 필요한 실패 구간만 읽는다.

최종 보고에는 다음 내용을 포함한다.

1. 해결한 문제와 분리한 책임.
2. 주요 변경 파일과 분리 근거.
3. 동작 보존 검증: 검사별 통과·실패·미실행, 기존/신규 실패, 근거 경로.
4. 남은 위험, 검증 한계, 별도 버그·기능 개선과 후속 작업.

소스 검사, 타입 검사, 테스트, 빌드, 런타임 관찰과 실제 기기 검증을 구분한다. 검증이 막힌 상태를 전체 완료로 보고하지 않는다.
