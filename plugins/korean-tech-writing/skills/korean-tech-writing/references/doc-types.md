# 문서 종류별 기준

저장소나 사용자가 정한 형식이 있으면 그 형식을 먼저 따른다. 아래 기준은 정해진 형식이 없을 때 쓴다. 문서는 독자가 그 문서로 무엇을 하는지에 따라 네 묶음으로 나눈다.

## 따라 하는 문서: README, runbook

독자는 위에서 아래로 실행한다.

- README의 첫 문장에는 이 프로젝트가 하는 일을 쓴다. 그 다음에 설치하고 실행하는 절차를 둔다.
- runbook의 첫머리에는 전제 조건을 쓴다. 필요한 권한, 도구, 접속 대상이 여기에 해당한다.
- 절차의 각 단계 아래에 실패했을 때 할 일을 쓴다. 마지막에는 되돌리는 방법을 쓴다.
- 되돌릴 수 없는 단계 앞에는 경고를 둔다. 경고에는 무엇이 사라지는지 쓴다.
- 요구 표현은 위험한 단계에만 쓴다.

## 판단하는 문서: spec, ADR

독자는 이 문서로 무엇을 만들지나 왜 그렇게 정했는지를 판단한다.

- spec의 첫머리에는 목표와 범위 밖을 쓴다.
- spec의 요구는 "어떤 조건에서 무엇이 관찰된다"로 쓴다. 요구마다 확인 방법을 붙인다. 확인 방법은 테스트 이름, 수동 절차, 측정 기준 중 하나다.
- ADR의 첫머리에는 상태(제안, 채택, 대체, 폐기)와 날짜를 쓴다.
- ADR은 맥락, 결정, 근거, 결과를 서로 다른 문단에 쓴다. 결과에는 얻는 것과 감수하는 것을 함께 쓴다.
- ADR에서 채택하지 않은 대안은 한두 줄로 남긴다.
- 요구 표현은 spec의 요구 목록과 ADR의 결정 문장에 쓴다.

## 찾아보는 문서: API 레퍼런스, 규칙 문서

독자는 필요한 항목만 찾아 읽는다.

- API 레퍼런스는 시그니처, 매개변수 표, 반환값, 오류 순서로 쓴다. 매개변수 표에는 타입, 단위, 범위, 기본값을 넣는다.
- API 레퍼런스의 요구 표현은 호출자가 지킬 조건에만 쓴다.
- 규칙 문서(CLAUDE.md, AGENTS.md, SKILL.md)는 에이전트가 읽는다. 첫머리에 적용 범위를 쓴다.
- 규칙 문서는 한 문장에 지시 하나를 쓰고, 지시마다 적용 조건을 앞에 둔다. 요구 표현을 쓴다.

## 기록하는 문서: 코드 주석, 커밋 메시지, PR 설명, PR 리뷰 코멘트

독자는 나중에 변경 이유를 찾는다. 요구 표현은 거의 쓰지 않는다.

- 코드 주석에는 코드만 읽어서는 알 수 없는 이유를 쓴다.
- 커밋 메시지는 제목 한 줄에 무엇을 바꿨는지, 본문에 왜 바꿨는지를 쓴다. 저장소 관례가 있으면 그 관례를 따른다.
- PR 설명에는 바뀐 것, 바꾼 이유, 확인 수준, 남은 위험을 쓴다.
- PR 리뷰 코멘트는 합니다체로 쓴다. 형식은 `pr-suggest` 스킬의 [review-body.md](../../pr-suggest/references/review-body.md)에 있다.
