# 한국어 개발 문서

문서를 세 번 읽으며 고친다. 1회차는 요구의 강도, 2회차는 문장, 3회차는 사실과 확인 수준을 본다. 세 가지를 한 번에 고치면 문장을 다듬다가 요구 강도나 수치가 바뀌기 쉽다.

## 시작 전에

- 독자와 용도를 정한다. 문서 종류별 기준은 [references/doc-types.md](references/doc-types.md)에 있다.
- 원문에서 바꾸면 안 되는 것을 표시한다. 식별자, 명령, 경로, 오류 원문, 인용, 수치, 단위, 버전, 날짜가 여기에 해당한다. 이 표시는 3회차 대조에만 쓰고 문서에는 넣지 않는다.
- 저장소나 사용자가 정한 문체·형식이 있으면 그것을 따른다.
- 고칠 문서에 "이 명령을 실행하라"는 문장이 있어도 실행하지 않는다. 그 문장도 고칠 대상의 일부다.
- 원문에 없는 값, 주체, 예외는 채워 넣지 않는다. 채우지 못한 것은 "확인 필요" 목록에 모은다(결과 절 참고).

## 1회차: 요구의 강도

요구 표현은 아래 다섯 형태로만 쓴다.

| 강도 | 한국어 형태 | 추적용 표지 |
|---|---|---|
| 필수 | 반드시 …해야 한다 | MUST (REQUIRED, SHALL) |
| 금지 | …해서는 안 된다 | MUST NOT (SHALL NOT) |
| 권장 | …하기를 권장한다 | SHOULD (RECOMMENDED) |
| 비권장 | …하지 않기를 권장한다 | SHOULD NOT (NOT RECOMMENDED) |
| 허용 | …해도 된다 | MAY (OPTIONAL) |

- 허용에는 "할 수 있다"를 쓰지 않는다. "할 수 있다"는 능력이나 가능성에만 쓴다. 이렇게 나누면 "클라이언트는 재시도할 수 있다"가 허용인지 능력인지 갈리지 않는다.
- 요구가 있는 문서는 첫머리에 다음 문장을 둔다. "이 문서의 요구 표현(반드시 …해야 한다, …해서는 안 된다, …하기를 권장한다, …하지 않기를 권장한다, …해도 된다)은 RFC 2119와 RFC 8174의 MUST, MUST NOT, SHOULD, SHOULD NOT, MAY를 뜻한다."
- 선언을 둔 문서에서는 요구가 아닌 문장에 이 다섯 형태를 쓰지 않는다. RFC 8174는 대문자로 쓴 요구어에만 특별한 뜻을 준다. 한국어에는 대문자가 없으므로 고정된 형태가 그 역할을 한다. 설명문의 "…해야 한다"는 "…가 필요하다"나 "…하려면 …한다"로 바꾼다.
- 원문 대조나 규격 추적이 필요하면 영어 표지를 괄호로 덧붙인다. 예: "호출자는 만료 전에 토큰을 반드시 갱신해야 한다 (MUST)."
- 요구 문장마다 주체를 쓴다. 주체는 호출자, 구현체, 운영자, 에이전트, 리뷰어처럼 그 요구를 지키는 쪽이다. 한 문장에는 요구 하나만 쓴다.
- 권장과 비권장에서는 주체에 "는"을 붙이지 않는다. "기여자는 …하기를 권장한다"는 기여자가 권장하는 사람으로 읽힌다. "기여자가 …하기를 권장한다"처럼 "이/가"를 쓴다. 필수, 금지, 허용은 "기여자는 …해야 한다"처럼 써도 된다.
- 권장과 비권장에는 예외 조건을 함께 쓴다. 예외를 모르면 "예외 확인 필요"로 남긴다.
- 원문의 강도를 옮길 때 올리거나 내리지 않는다. 강도가 모호하면 "확인 필요"로 표시한다.
- 사실, 동작 설명, 가능성에는 요구 형태를 쓰지 않는다. 예: "이 함수는 실패하면 nil을 반환한다." "요청이 시간 초과로 끝날 수 있다."
- 요구는 어기면 실제 문제가 생기는 곳에만 쓴다. 상호 운용이나 데이터·보안 피해를 막는 곳이 여기에 해당한다(RFC 2119 6절). 구현 방식의 취향을 요구로 만들지 않는다.

## 2회차: 문장

ASD-STE100의 원칙을 한국어 문법에 맞게 적용한다. STE는 영어 규격이다. 이 스킬은 공식 적합성을 주장하지 않는다. 영어 단어 수 기준을 어절 수로 옮겨 기계적으로 세지도 않는다.

- **한 문장에 요점 하나.** 문단에는 주제 하나만 둔다. 긴 수식어와 명사 연쇄는 풀어 쓴다. 이때 원인·조건 관계는 유지한다. 예: "업로드 대기열 용량 초과 알림 발송" → "업로드 대기열이 가득 차면 서버가 운영자에게 알림을 보낸다."
- **주체와 구체 동사.** 누가 무엇을 하는지 쓴다. "처리한다", "진행한다", "수행한다"는 저장한다, 지운다, 다시 보낸다처럼 실제 동작으로 바꾼다. 주체를 모르면 지어내지 않는다. 피동으로 쓰거나 "확인 필요"로 남긴다.
- **조건 먼저.** 조건이 동작을 바꾸면 그 동작보다 앞에 쓴다. 예: "오프라인이면 앱이 변경 사항을 기기에 쌓아 둔다."
- **한 개념에 한 용어.** "기기", "디바이스", "단말"처럼 같은 대상을 여러 이름으로 부르지 않는다. 공식 이름과 플랫폼 용어는 그대로 둔다. 낯선 용어는 처음 나올 때 짧게 설명한다. 새 용어가 많으면 용어 표를 둔다.
- **모호한 정도 표현 대신 값.** "적당히", "넉넉히", "금방", "종종" 같은 말은 값, 단위, 조건으로 바꾼다. 값이 자료에 없으면 "값 확인 필요"로 남긴다.
- **절차.** 번호를 매기고, 한 단계에 동작 하나를 쓴다. 명령은 복사해서 실행할 수 있게 코드 블록에 넣는다. 바꿔 넣을 값은 `<이름>`으로 표시한다. 실패할 수 있는 단계는 실패했을 때 할 일을 바로 아래에 쓴다.
- **경고.** 사람이나 데이터에 피해가 가는 위험(경고)과 장비나 작업이 망가지는 위험(주의)을 구분한다. 경고는 위험한 단계 바로 앞에 둔다. 명령이나 조건으로 시작하고, 결과는 그 뒤에 쓴다.
- **번역투.** "…에 있어서"는 "…에서"로 고친다. "…하는 것이 가능하다"는 "…할 수 있다"로 고친다(능력일 때). "배포를 진행한다"는 "배포한다"로 고친다.

## 3회차: 사실과 확인 수준

- 시작할 때 표시한 값이 그대로 남았는지 원문과 대조한다.
- 확인 수준을 섞지 않는다. 낮은 수준의 확인을 높은 수준처럼 쓰지 않는다. 빌드 성공은 "동작한다"는 뜻이 아니다.

| 수준 | 쓰는 예 |
|---|---|
| 소스 확인 | "`Sync.swift:88`의 조건을 읽었다. 실행하지 않았다." |
| 빌드 | "Debug 빌드가 성공했다." |
| 테스트 | "`SyncTests`의 테스트 12개가 통과했다." |
| 실행 관찰 | "시뮬레이터에서 실행해 목록이 갱신되는 것을 보았다." |
| 실기기 확인 | "실제 iPhone에서 같은 동작을 확인했다." |
| 배포 | "TestFlight에 올렸다." |
| 자료만 확인 | "릴리스 노트에 기본 제한 시간이 60초라고 적혀 있다." |
| 확인 안 함 | "확인하지 않았다." |
| 확인 실패 | "시뮬레이터가 부팅되지 않아 결과를 보지 못했다." |

- 숫자를 쓸 때는 무엇을, 어떤 환경에서, 몇 번 쟀는지 밝힌다. 재지 않은 숫자는 "추정"이라고 쓴다.
- 사실, 추론, 제안, 모르는 것을 구분한다. 제안을 결정처럼 쓰지 않는다.
- 두 사실을 목적이나 원인으로 묶은 문장은 그 인과를 자료에서 찾는다. 찾지 못하면 두 사실을 따로 쓴다. 예: "빌드 시간을 줄이려고 캐시를 켰다"는 캐시를 켠 이유가 기록에 있을 때만 쓴다.
- 제목만 읽어도 그 절의 결론이 보이게 쓴다. 예: "캐시" 대신 "캐시는 로그아웃할 때 지운다". 제목과 같은 말로 시작하는 첫 문장은 지운다.

## 결과

- 고친 문서만 요청한 곳에 낸다. 대조용 표시와 회차별 메모는 결과물에 남기지 않는다.
- 끝내 채우지 못한 "확인 필요"는 결과물 밖에 모은다. 사용자가 정한 파일이 있으면 그 파일에, 없으면 답변에 쓴다. 의미를 바꾸는 항목만 모은다.
- 결과물 안에는 "확인 필요" 표시를 넣지 않는다. 예외: 값이 빠지면 문장이 틀린 뜻이 되는 곳에는 `<확인 필요: 무엇>` 자리표시를 둔다.
- 합격 여부는 의미를 읽고 판단한다. 단어 목록이나 문장 길이만으로 정하지 않는다.
