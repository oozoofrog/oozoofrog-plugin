# 리뷰 본문 형식

본문은 요약 한 문장, 사실표, 적용 안내 순서로 쓴다. 받는 사람이 표 한 개만 읽고 적용 여부를 정할 수 있어야 한다. 문장 규칙은 같은 Plugin의 `korean-tech-writing` 스킬을 따른다.

## 틀

꺾쇠 안의 값은 실제 값으로 바꾼다. 값이 없는 행은 지운다.

```markdown
@<작성자> <대상>에 대한 개선안 <N>건을 suggestion으로 남깁니다. 머지를 막는 의견은 아닙니다.

| 항목 | 내용 |
|---|---|
| 문제 | <지금 코드의 상태. 파일과 심볼을 밝힌다> |
| 영향 | <그 상태가 일으키는 일. 확인한 범위만> |
| 바꾸는 것 | <무엇을 지우고 무엇으로 대신하는지> |
| 동작 변화 | <없음, 그리고 그 근거> 또는 <바뀌는 동작> |
| 범위 | 파일 <F>개, +<A>/−<D>줄, 테스트 <변경 여부> |
| 확인 수준 | 재적용 일치(head `<SHA 앞 8자리>`) · 빌드 <실행함/실행 안 함> · 테스트 <실행함/실행 안 함> |

Files changed 탭에서 suggestion을 batch에 모두 담고 한 커밋으로 반영해 주세요.
```

조건이 맞을 때만 아래 문장을 덧붙인다.

- 일부만 반영하면 빌드나 테스트가 깨질 때: "<N>개를 반드시 함께 반영해야 합니다 (MUST). 일부만 반영하면 <깨지는 것>."
- 마지막 승인 뒤에 큰 변경이 있었을 때: "@<리뷰어> <날짜> 승인 이후 <바뀐 것>이 추가되었습니다. 머지 전에 다시 보시기를 권장합니다. 예외: 이미 확인하신 경우."

## 쓰는 법

- 합니다체로 쓴다. 저장소나 사용자가 다른 문체를 정했으면 그 문체를 쓴다.
- "문제"와 "영향" 행에는 코드에서 확인한 사실만 쓴다. 셀 수 있는 것은 센 범위와 함께 쓴다. 예: "같은 날짜 형식 문자열이 이 PR의 파일 3곳에 있습니다."
- "동작 변화" 행은 비워 두지 않는다. 동작이 같다고 쓰려면 근거로 코드 위치를 든다.
- "확인 수준" 행에는 실행한 것과 실행하지 않은 것을 모두 쓴다. 재적용 일치는 `suggest.py`의 검사를 뜻하며 빌드나 테스트가 아니다.
- 인라인 코멘트의 설명은 그 줄에만 해당하는 근거 1~2문장이다. 표의 내용을 되풀이하지 않는다.
- 이모지와 감탄 표현은 쓰지 않는다.

## 고치기 전·후

| 고치기 전 | 고친 문장 |
|---|---|
| 이 부분 상수로 빼면 좋을 것 같아요~ | 문제: `"yyyy-MM-dd"`가 이 PR의 파일 3곳에 따로 적혀 있습니다. 영향: 형식을 바꿀 때 3곳을 모두 찾아 고쳐야 합니다. |
| 아마 영향 없을 거예요. | 동작 변화: 없음. 세 곳 모두 같은 `DateFormatter` 설정을 씁니다(`Report.swift:31`, `Export.swift:12`, `Share.swift:48`). |
| 확인했습니다! | 확인 수준: 재적용 일치(head `1a2b3c4d`) · 빌드 실행 안 함 · 테스트 실행 안 함 |
