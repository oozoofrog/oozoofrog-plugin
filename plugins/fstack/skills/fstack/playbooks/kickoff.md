### Kickoff
**You own the map of intent. The user owns the decisions. Write no code.**

1. Read the inputs. Cite each input by URL plus commit, or by repo-relative path.
2. Do not create rule files or journal files without the user's consent (G3).
3. If the request could name more than one problem, list the two or three candidate problems. Give each one the term that names it and the sign that tells it apart from the others. Recommend the most likely one and say why. For a choice of purpose, preference or scope, the recommendation is not a decision: the user makes it in step 7.
4. Restate the request in the practitioner's terms. Use the expert terms that change what gets built. Add what a top practitioner would add: a primary source instead of a digest, a method, and a check from outside this session. Open each link that you cite and confirm that it says what you claim; cut what you cannot confirm. Offer the rewritten request to the user.
5. Write five parts: facts read, hypotheses (labeled Inferred), gaps, ideas and open questions. Put them in a file only at T2 or on request. Otherwise put them in the reply.
6. Settle each question that a run can answer with `playbooks/prototype.md`.
7. Ask the user-owned questions once, as one batch of numbered questions. Ask about the purpose first. Then ask each remaining choice that changes what gets built as its own question; do not fold them into one pick among the candidates. If the answers are not in this turn, skip step 8, start no work that depends on them, and end the report with the questions.
8. Record the answers. Strike rejected ideas through. Do not delete them.
9. Reread the result for contradictions, hidden questions and counterexamples.
10. Run `playbooks/wrap-up.md`.

**Report:** candidate problems and the pick, the rewritten request, closed and open questions, prototypes built, rejected ideas, assumptions.
