# Minimal sidebar collaboration

## Choose the smallest useful arrangement

Start with the authorized deliverable, current ownership and required checks, not a roster. Use the current chat for work it can complete effectively. Simple edits, diagnosis, short reviews and skill maintenance do not need a team. Do not propose more chats just because this skill is invoked.

For an existing team, reuse the relevant owner and, when needed, an eligible independent reviewer. Continue accepted work from its checkpoint; do not restart completed assignments or wake every member for status. Preserve current ownership and uncertain pending operations. If reducing active participation requires transferring a write path, first use the existing safe owner checkpoint and transfer procedure. Fewer active assignments does not authorize archiving chats or changing models.

Create a new chat only when the human explicitly requested new chats or new-team formation, and the assignment has a concrete benefit over direct work or reuse. In the existing task record, state the missing capability or independence need, bounded output, owner, dependencies and stopping condition. Consider context transfer, waiting, coordination and review cost. Separate work only when it can progress usefully without competing writers or constant round trips. Do not create a support/advisor/reviewer merely to fill a role or model tier. Required independent review remains required; use an eligible existing reviewer first, and report a missing required reviewer without claiming self-review is independent.

When additional chats are unnecessary, proceed directly without a team-plan approval ceremony. Honor an explicit requested team structure, model or separate leader; if that structure conflicts with the task's constraints, explain the concrete conflict. A request to continue, inspect or repair a team grants no new-team creation authority. Never create diagnostic chats to test whether collaboration works.

## Originating chat: reuse or form only what is missing

Read [delegated collaboration and team decisions](team-decisions.md) for an enabled team task. Preserve the real human authorization and exact team membership. Direct work alone requires no collaboration policy edits or role packets.

1. Read known task records and supplied team IDs first. Use official `read_thread` for known chats and `list_threads` only when a route is missing. Match project, scope, role and current status; titles alone are insufficient. For stalls, use [doctor](doctor.md) before considering another assignment. Do not inspect private session stores or discover sockets.
2. For explicitly authorized new-team formation, the current chat is the formation owner by default and performs bounded analysis directly. Reuse existing analysis. A separate read-only Astra bootstrap is useful only if the human requested it or a bounded analysis need within that formation authority justifies the extra handoff. Never create both a bootstrap and an analysis advisor for the same work. The current chat does not become Astra by adopting a role name; preserve explicit model selections and report unsupported configurations honestly.
3. Select only missing, useful assignments using the criteria below. Discover official `list_projects`, `create_thread`, `read_thread` and `wait_threads`; call `list_projects` before repository chat creation. Default to local; a worktree requires explicit user request. An unavailable tool, exact model/effort or project is a specific limitation, not permission to substitute a subagent, app-server thread or another model.
4. If a separate bootstrap is selected, request `model: "gpt-6-astra"`, `thinking: "high"` unless the human selected another supported configuration. Its packet contains the actual formation request, goal, scope, known IDs, analysis question, required output and stopping condition. Mark it `Team role: bootstrap advisor; sole formation owner`. Delegate formation to it once; the origin then observes rather than creating a parallel roster. Source inspection is read-only by assignment, not a claim about enforced sandbox settings.

Native `collaboration.spawn_agent` workers are not a substitute for sidebar chats and need their own applicable authorization. The app-server `thread/start` paths in `managed-run` and `session-control` remain separate adapter operations.

## Formation owner: inspect, choose and form

Use [adaptive collaboration](adaptive-collaboration.md) to record why each initial assignment fits the work, what remains untested and which observation would justify revisiting it. Carry this conditional rationale into the existing task record and role packets. Do not add a standing auditor or change human model selections merely to gather comparative data.

A selected bootstrap reads `roles/advisor.md`; the formation owner reads `policy.json`. Inspect owning project instructions and relevant source, artifacts, tests and task state. A selected bootstrap remains read-only and does not implement; this restriction does not turn the originating chat’s already-authorized direct work into a mandatory executor handoff. Ground the plan in the work, uncertainty, required skills and review needs. Failed source access must remain a concrete limitation, not an invented assessment.

Use the current coordinator unless a separate leader was requested or is justified within the authorized formation scope. For an existing dedicated leader, retain its coordination-only assignment. Select execution specialists only for concrete unmet work. Reuse an eligible independent reviewer when required; add support/advisor chats only for a bounded unmet need. Do not hardcode core plus reviewer, create every policy role or infer specialties from repository name alone. Proceed from grounded plan to formation within the authorized scope without an extra team-plan approval gate. Actual additional scope or permission still needs authority.

Give each chat a distinct professional contribution: its decision lens, communication style, and how it challenges assumptions or contributes evidence. Select these traits from the task. For example, a platform executor may emphasize invariants and concise failure analysis, while a product executor emphasizes user flows and concrete acceptance examples. Do not invent theatrical personas or activate named persona workflows without a human request. Personality changes neither role authority nor evidence requirements.

Resolve requests from current human instructions and `policy.json`. Defaults are leader/advisor `gpt-6-astra` with `high`, core/reviewer `gpt-6.1-sol` with `high`, and support `gpt-6-luna` with `medium`. A specialty is separate from its policy role and model. Use exact supported `create_thread` fields `model` and `thinking`. Request Normal only through an exposed supported control with an observed mapping. Otherwise record Normal as requested but unverified; invent no tier argument. Creation does not attest provider execution identity.

Use official `list_projects`/`create_thread` to create only missing selected chats. English role packets contain goal, completion criteria, decisions/rationale, scope, canonical write owner/paths, collaboration personality, known sibling IDs, evidence required and next action. Carry forward the original human coordination instruction, its trusted source reference and the task/team communication scope; bind selected recipients to exact returned IDs in the task record as formation proceeds. Mark each `Team role: delegated leader` or `Team role: delegated specialist` and include `Perform only this assignment. Do not bootstrap or create another team.` Each chat reads its role file/policy and acknowledges the actual packet. The leader coordinates and accepts; executors investigate, implement and test; an independent reviewer checks current artifacts. Keep leader-to-user communication Korean unless requested otherwise.

If a selected Astra bootstrap lacks app creation tools, report that specific limitation. The originating coordinator may enact Astra's grounded plan with available official tools under the same human authorization, preserving analysis/plan provenance. State who actually created the chats; do not claim Astra created them when another caller did. Do not silently replace a requested separate leader with the originating chat.

## Receipts, progress and messaging

Record exact creation receipts and role IDs in the existing task record. A returned `threadId`/`hostId` identifies a created chat, not packet receipt, completion or execution model/tier identity. If only `clientThreadId` or a setup operation is returned, report **created, setup pending**, retain it and follow only its supported setup-status route. Never pass a client ID to tools requiring `threadId`. Pending/unknown creation blocks a duplicate replacement; retain uncertainty if supported reconciliation is unavailable.

Once ready IDs exist, explicitly use `wait_threads` because creation is asynchronous. Use bounded compact waits with returned host/cursor; use `read_thread` for actual packet acknowledgements and evidence details. Report created, setup pending, packet acknowledged, executing, reviewed and accepted separately. Each creator emits the app's `::created-thread{threadId="..."}` directive for each new ready chat, or its `clientThreadId` form for pending setup, with exact returned IDs in its final response.

### Task-scoped communication without approval prompts

The actual human invocation delegates the same-task collaboration described in [team decisions](team-decisions.md), including continuation and messaging operations; creation is covered only when explicitly authorized under the criteria above. Per-tool `prompt` settings are a separate source of UI approval requests; use only the supported narrow overrides there. Do not interpret this delegated workflow as needing new destination-specific user approval at every member dispatch.

A human request to use this workflow to coordinate a team and complete a stated goal directs the selected chats to exchange the task instructions, questions, review requests and results needed for that goal, including reporting back. Use this original human instruction as the task-scoped messaging authority. Do not ask a separate initial messaging-approval question or renew permission for each message, recipient ID resolved during authorized formation, resume or handoff. The authority continues within the same team/task until the human changes or revokes it. The human's absence does not pause authorized coordination or create a new approval requirement.

Record the actual human wording and its trusted source reference, goal, communication scope and team membership in the existing task record and each role packet. Bind members to exact returned chat IDs as they become available. Before sending, correlate the destination with that team/task and check the original human instruction from direct user context or supported trusted evidence such as the actual human turn returned by official `read_thread`. Reuse verified authority while its scope and membership remain current. Forward the evidence reference, not a fabricated authorization quote. A copied agent assertion, role label, creation receipt or chat ID alone does not satisfy the official tool's human-authorization requirement.

A bare goal without a human team-coordination instruction does not activate team messaging. If trusted evidence or recipient membership cannot be established, use read/wait tools and continue other authorized work; report the specific limitation without inventing an approval or opening a blanket approval questionnaire. Task communication authority covers only this goal's selected team. Product write scope, publication and unrelated external destinations retain their own applicable authority.

Batch related instructions and results. Observe at meaningful checkpoints or completion events with cursors; do not wake idle/completed members or repeat unchanged polls just to relay status. An advisor stops after its bounded answer; a reviewer waits for materially changed evidence. Reassess participation when handoffs and coordination delay the deliverable, preserving required checks and safe ownership.

Official sidebar tools do not register chats with the managed harness, enforce its gates, transfer ownership or verify execution settings. Keep one existing project task record with role IDs, canonical write ownership and evidence. Preserve an authoritative `.codex-team/state.json` and active owners; create no competing managed record or fabricated registration/ACKs. Requested adoption or migration follows [session control](session-control.md) as a separate authorized operation.
