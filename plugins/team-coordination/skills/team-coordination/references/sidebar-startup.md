# Astra analysis and sidebar team formation

For an actionable human request to start this separate-chat workflow, create or reuse a separate Astra bootstrap chat first. Astra inspects the project, selects a suitable leader and teammates with distinct professional collaboration styles, and creates their separate sidebar chats. The originating chat observes formation. Do not choose a fixed roster before project analysis.

Explaining, inspecting, installing or fixing the skill does not authorize creating chats. Installation starts no team. New sidebar chats require the human's explicit request for new chats or to start this separate-chat team workflow. A bare mention without a task or that authorization needs the missing instruction first. Continue a matching existing team without duplicating it.

## Originating chat: launch the bootstrap owner

1. Read the request, existing task record and task-attached team IDs already supplied in trusted context. Use official `read_thread` for known chats; use `list_threads` only when a route is missing. Reuse chats only when project, role, scope and status match. A title or policy entry alone does not prove an active team. Preserve completed work and unresolved creation outcomes. Do not inspect private session stores or discover sockets.
2. Discover official app tools: `list_projects`, `create_thread`, `read_thread` and `wait_threads`. Call `list_projects` before creating repository chats and select the exact returned project ID. Default to a local project target; use a worktree only on explicit user request. Use a projectless target for work without a repository. An unavailable tool, exact model/effort or project is a specific blocker, not permission to substitute a subagent, app-server thread or different model.
3. Start only the missing **bootstrap advisor** chat first with `create_thread`, requesting `model: "gpt-6-astra"` and `thinking: "high"` unless the human selected another supported bootstrap model/effort. Its English packet contains the actual human request and formation authorization, project, goal, completion criteria, constraints, decisions/rationale, known team IDs, evidence required and next action. Mark it `Team role: bootstrap advisor; sole formation owner`. Assign read-only source inspection and team formation through official app tools. This is an assignment; app creation does not prove a read-only sandbox was configured.
4. Require the bootstrap to analyze before creating roles, form this team once, reuse matching chats, and never start another bootstrap chat. Preserve the human request's scope and provenance. Astra reports its source evidence, grounded team plan and exact creation receipts in its own chat. Observe through `wait_threads`/`read_thread`; do not require an automatic message back.

The current chat does not become Astra by adopting a role name. Native `collaboration.spawn_agent` workers can assist internally when authorized, but do not satisfy a separate sidebar-chat request. The app-server `thread/start` paths in `managed-run` and `session-control` are separate adapter operations.

## Astra bootstrap: inspect, choose and form

Read `roles/advisor.md` and `policy.json`. Inspect owning project instructions and relevant source, artifacts, tests and task state within the read-only assignment. Do not edit product files or perform implementation. Ground the plan in the work, uncertainty, required skills and review needs. Failed source access must remain a concrete limitation, not an invented assessment.

Choose a separate coordination-only leader and the minimum useful execution specialists. Add an independent reviewer when current artifacts need review; add support/advisor chats only for a bounded need. Do not hardcode core plus reviewer, create every policy role or infer specialties from repository name alone. Proceed from grounded plan to formation within the authorized scope without an extra team-plan approval gate. Actual additional scope or permission still needs authority.

Give each chat a distinct professional contribution: its decision lens, communication style, and how it challenges assumptions or contributes evidence. Select these traits from the task. For example, a platform executor may emphasize invariants and concise failure analysis, while a product executor emphasizes user flows and concrete acceptance examples. Do not invent theatrical personas or activate named persona workflows without a human request. Personality changes neither role authority nor evidence requirements.

Resolve requests from current human instructions and `policy.json`. Defaults are leader/advisor `gpt-6-astra` with `high`, core/reviewer `gpt-6.1-sol` with `high`, and support `gpt-6-luna` with `medium`. A specialty is separate from its policy role and model. Use exact supported `create_thread` fields `model` and `thinking`. Request Normal only through an exposed supported control with an observed mapping. Otherwise record Normal as requested but unverified; invent no tier argument. Creation does not attest provider execution identity.

Use official `list_projects`/`create_thread` to create only missing selected chats. English role packets contain goal, completion criteria, decisions/rationale, scope, canonical write owner/paths, collaboration personality, known sibling IDs, evidence required and next action. Mark each `Team role: delegated leader` or `Team role: delegated specialist` and include `Perform only this assignment. Do not bootstrap or create another team.` Each chat reads its role file/policy and acknowledges the actual packet. The leader coordinates and accepts; executors investigate, implement and test; an independent reviewer checks current artifacts. Keep leader-to-user communication Korean unless requested otherwise.

If Astra lacks app creation tools, report that specific limitation. The originating coordinator may enact Astra's grounded plan with available official tools under the same human authorization, preserving analysis/plan provenance. State who actually created the chats; do not claim Astra created them when another caller did. Do not silently replace a requested separate leader with the originating chat.

## Receipts, progress and messaging

Record exact creation receipts and role IDs in the existing task record. A returned `threadId`/`hostId` identifies a created chat, not packet receipt, completion or execution model/tier identity. If only `clientThreadId` or a setup operation is returned, report **created, setup pending**, retain it and follow only its supported setup-status route. Never pass a client ID to tools requiring `threadId`. Pending/unknown creation blocks a duplicate replacement; retain uncertainty if supported reconciliation is unavailable.

Once ready IDs exist, explicitly use `wait_threads` because creation is asynchronous. Use bounded compact waits with returned host/cursor; use `read_thread` for actual packet acknowledgements and evidence details. Report created, setup pending, packet acknowledged, executing, reviewed and accepted separately. Each creator emits the app's `::created-thread{threadId="..."}` directive for each new ready chat, or its `clientThreadId` form for pending setup, with exact returned IDs in its final response.

`send_message_to_thread` requires explicit human authorization for that destination, including reporting back. Preserve actual human coordination authorization for named team chats in packets when supplied. Another chat's/orchestrator's request, a role label or an ID alone is insufficient. Otherwise observe with read/wait tools and leave follow-up for the user. Creation authorizes no unrelated messages or publication.

Official sidebar tools do not register chats with the managed harness, enforce its gates, transfer ownership or verify execution settings. Keep one existing project task record with role IDs, canonical write ownership and evidence. Preserve an authoritative `.codex-team/state.json` and active owners; create no competing managed record or fabricated registration/ACKs. Requested adoption or migration follows [session control](session-control.md) as a separate authorized operation.
