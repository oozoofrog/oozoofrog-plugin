# Requested profiles and configured evidence

Leader/design/advisor defaults request `gpt-6-astra` with reasoning `high`; core/reviewer request `gpt-6.1-sol` with reasoning `high`; support requests `gpt-6-luna` with reasoning `medium`. Every role requests service mode `normal`. Model, reasoning effort and service mode are separate fields. Choose supported reasoning effort to fit task difficulty; do not automatically restore ultra or Fast defaults. Advisor implementation is still prohibited.

Normal means the official Codex app-server explicit Standard request. It does not require a literal Normal catalogue entry: `model/list.serviceTiers` advertises additional tiers, and priority-only or empty additional tiers do not establish that Standard is unsupported. The exact model and reasoning effort still require current catalogue support. Explicit Fast remains opt-in and resolves only from one exact Fast catalogue label and its nonempty ID; there is no fallback.

The current client contract is `codex-app-server-0.163.0-alpha.11.2`, based on that version's generated schema. The official CLI factories select this client contract for owned stdio and explicitly authorized native proxy connections; the endpoint must implement the same contract. This is a client contract selection, not negotiated server capability or tier attestation. Arbitrary or legacy Controller transports without this selected contract fail as unsupported/unknown protocol before Standard dispatch. A field rejection stops the operation without resubmission using omission, inherited tier or Fast.

Every new owned idle Normal turn, including managed task, ordinary task, packet and configuration-check turns, sends `serviceTierForTurn: "default"` and omits persistent `serviceTier`. Omitted or null `serviceTierForTurn` inherits the thread tier; this adapter uses neither for a Normal request. The override does not change persistent thread settings or a turn being steered. Normal thread creation itself sends no persistent tier override and performs no inference. The existing thread tier can remain unknown or Fast while a new turn explicitly requests Standard.

Keep field-specific semantics separate: `turn/start.serviceTier` applies persistently to that and subsequent turns; `thread/settings/update.serviceTier: null` clears the persistent setting, while omission leaves it unchanged. These are not interchangeable with turn-local null inheritance. No settings mutation, resume or inference is performed merely to discover a native session's tier. Start/resume nullable types alone do not establish null inheritance/clear semantics.

Session control `change --service-tier normal` records a pending request; `apply-change` sends the new-turn Standard override at an owned idle boundary with the requested model and reasoning effort. Each later Normal task turn sends its own explicit override. `verification_scope.service_tier: accepted_per_turn_only` means the request was acknowledged; persistent configured tier and provider execution remain unavailable. Compatibility state names such as `configuration_verified_after_turn` verify observed model/reasoning settings, not persistent Normal or actual provider execution. Explicit Fast preserves its existing persistent configuration/check path.

`thread/read` exposes no tier. Missing/null start/resume receipts remain unavailable, never inferred Normal. Exact-thread settings notifications are configured observations, not execution telemetry. Accepted requests, configured settings and live provider execution are separate evidence. The official public [0.162.1 resolver regression](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/protocol/src/openai_models.rs#L1957-L1973) independently explains why explicit Standard works with a priority-only catalogue and priority default. It is a different source version from the selected 0.163 client contract. The Codex `default` sentinel is not a claim that a raw Responses API `service_tier` field contains the literal string `default`.

The current native app messaging API exposes model/thinking but no tier setter or settings readback. Relayed instructions are requests, not per-session verification. Do not wake completed tasks or replay work to simulate a settings update. Active-turn settings are not changed by next-turn requests.

## Separate requested-default overlay

From a verified bundle use `run.py profile-overlay --codex-home ABS --profile REQUESTED_JSON plan`, then `apply`. The JSON schema is 1, `execution_authorized` is false, and `adoption` is `pending_explicit_owner_safe_boundary`. All five role objects contain their exact model, reasoning effort and Normal request above. An older installed overlay is not silently replaced; preserve its journal and use an exact reviewed configuration migration. Keep catalogue evidence distinct from configured settings.

The overlay appends a discoverable directive outside the existing managed AGENTS block, writes `team-coordination-desired-profiles.json` outside the installed skill, and uses its own `team-coordination-profile-defaults-install.json` journal. It installs future instruction defaults only. Existing project contracts and actual native session configuration remain pending explicit safe owner adoption; completed projects are not rerun. The overlay source-runtime version is provenance, not evidence of the installed runtime version.

Use `profile-overlay ... doctor` for overlay integrity. The original runtime doctor must also pass with its original contract and journal unchanged. Rollback order is mandatory: first guarded `profile-overlay ... rollback`, then the original runtime rollback. Bare legacy rollback refuses while the extra AGENTS directive is present. Concurrent edits are preserved and require reconciliation. No historical journal is rewritten; no credentials, permissions or security configuration are changed.
