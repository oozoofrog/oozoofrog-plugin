# 문구 예시와 의미 검수

다음은 작성 원칙을 설명하려고 만든 예시다. 특정 제품의 실제 기능이나 성능을 입증하지 않는다.

| 맥락 | 다듬기 전 | 다듬은 예 | 지켜야 할 의미 |
|---|---|---|---|
| 자료 확인 제목 | 근거 범위 | 자료 확인 범위 | 어떤 자료를 확인했는지 설명하는 항목일 때 사용한다. 논증의 적용 범위라면 다른 뜻이므로 기계적으로 바꾸지 않는다. |
| 구성 예시 제목 | 출처 기반 참고 세팅 | 세팅 예시 | 본문에서 필요한 출처와 적용 조건을 보존한다. |
| 조건에 따른 구성 제목 | 출처에 있는 조건부 대안 | 상황에 따라 바꿔 쓰는 구성 | 조건을 삭제하거나 무조건 권장하는 구성으로 바꾸지 않는다. |
| 확인 상태 | A는 미검증, B도 미검증입니다. | A는 테스트하지 않았어요. B는 권한 오류로 결과를 확인하지 못했어요. | 각각의 확인 이력이 이와 같다는 자료가 있을 때만 풀어 쓴다. |
| 설정 화면 이동 버튼 | 더 스마트한 경험 시작 | 알림 설정 열기 | 다음 화면이 알림 설정일 때의 예다. 알림을 바로 켠다는 뜻이 아니다. |
| 저장 오류 | 파일 저장에 실패했어요. 다시 시도해주세요. 파일 저장을 위해 지금 바로 다시 시도해보세요. | 파일을 저장하지 못했어요. 다시 시도해 주세요. | 실패 상태와 가능한 복구 행동은 남긴다. 재시도가 가능한지는 실제 동작에 맞춘다. |
| 자료에 적힌 동작 | 소스 C에는 최대 3회 재시도한다고 적혀 있습니다. | 소스 C에는 최대 3회까지 다시 시도한다고 나와 있어요. | 실제 실행을 확인했다는 뜻으로 바꾸지 않는다. |

## 희망과 실제 동작 구별하기

입력: 홍보 문구는 ‘모든 알림을 놓치지 마세요’이고, 확인된 동작은 버튼을 누르면 알림 설정 화면이 열린다는 것뿐이다.

수정문: 버튼 ‘알림 설정 열기’. 설명이 필요하면 ‘알림 설정 화면으로 이동해요.’

설정 화면에서 어떤 기능을 바꿀 수 있는지는 덧붙이지 않는다. 사용자가 설명을 요청하지 않았고, 조건·부정·주의 등 필요한 정보가 없을 때만 중복 설명을 생략할 수 있다. 반대로 버튼이 알림을 즉시 켠다는 동작이 확인됐다면 ‘알림 켜기’라고 쓸 수 있다. 목적이나 효과를 설명할 근거가 있는 경우까지 지우지 않는다.

## 모르는 주체를 채우지 않기

입력: ‘업로드 후 관리자가 파일을 검토합니다. 이후 승인되며 삭제할 수 있습니다.’

수정문: ‘파일을 올리면 관리자가 검토해요. 승인 후 파일을 삭제할 수 있어요.’

별도 확인 사항: ‘승인하는 사람과 파일을 삭제할 수 있는 사람을 확인해야 해요.’

검토자가 승인한다거나 사용자가 삭제할 수 있다고 단정하지 않는다. 승인 후 삭제할 수 있다는 순서는 남기고, 모르는 주체만 확인 사항으로 분리한다. 실제 제품 문구를 수정할 때는 확인 전까지 모호한 원문을 몰래 확정하지 않는다.

## 짧게 써도 남겨야 할 차이

‘파일 삭제’와 ‘다운로드 제거’가 제품의 공식 명칭이면 유지한다. 전자는 같은 계정의 다른 기기에도 영향을 주고 후자는 현재 기기의 사본만 지운다는 자료가 있으면, 둘을 ‘파일 지우기’로 합치지 않는다. 명칭을 줄이는 것보다 동작의 차이를 이해시키는 편이 중요하다.

## 최종 대조

- 원문의 이름·수치·단위·날짜·출처·직접 인용을 보존했는가?
- 조건·예외·범위·의무·가능성·불확실성의 강도가 같은가?
- 시험하지 않음, 확인 실패, 자료 확인, 실제 동작 확인을 구별했는가?
- 확인되지 않은 주체·원인·권한·효과·추천이나 목적을 위한 행동 경로를 추가하지 않았는가? 편집 대상의 희망·홍보 문구를 사실로 취급하지 않았는가?
- 버튼이 실제로 하는 행동과 다음 화면을 예측하게 하는가?
- 공식 용어와 복구 안내를 남기면서 불필요한 반복만 줄였는가?
- 문맥과 기존 제품에 맞는 말투를 일관되게 썼는가?

검수는 의미를 읽고 판단한다. 단어 치환 비율이나 정규식 점수는 의미 보존과 자연스러움의 증거가 아니다.
